# 模块远程下载与发布流程

> 关联实现：`lib/core/rust/ModuleManifestClient.dart`、`lib/core/rust/ModuleDownloader.dart`、
> `lib/core/rust/ModuleLoader.dart`、`lib/core/rust/ModuleManifest.dart`、
> `generate_modules_manifest.sh`、`.github/workflows/build.yml`、
> `rust/gstore_host/src/trust.rs`。
> 计划来源：`.omo/plans/remote-plugin-download.md`。

## 1. 目标与边界

原生插件（`qr` / `analyzer` / `repo` / `download` / `llm`）不再只能随安装包内置。
应用会从**同一个 `sunO2/GStore` 的 GitHub Release** 检查并下载更新，校验完整性后加载；
内置版本始终保留为离线兜底。IT-Tools 离线包也走同一发布通道独立更新。

本阶段（Phase 1）的边界：

- **不做** Ed25519 签名校验，公钥仍为空（见 §6）。
- 远程下载**不走**用户下载管线：不产生下载中心任务、不弹通知、不调用 `InstallManager.installApk`。
- 后台只下载安装、**不挂载**，更新下次启动生效。
- 不改 C ABI / `gstore_contract` / `GSTORE_MODULE_ABI_VERSION`，不做第三方模块市场，不做运行期热替换。

## 2. 发布侧的资产与清单

### 2.1 资产命名

发布端资产名（Release asset name）由 `generate_modules_manifest.sh` 生成，**每 ABI 唯一**：

```
libgstore_mod_<name>_<major.minor.patch>-<abi>.so
```

- `<name>`：模块名，如 `qr`。
- `<major.minor.patch>`：三段纯数字版本，剥离 `+build` 与 `-pre.release` 元数据，不足三段补 0。
- `<abi>`：`arm64-v8a` / `armeabi-v7a` / `x86` / `x86_64`。

例：`libgstore_mod_qr_1.2.3-arm64-v8a.so`。

与本地落盘名的区别：

| 场景 | 文件名 |
| --- | --- |
| Release 资产 | `libgstore_mod_<name>_<major.minor.patch>-<abi>.so`（带 ABI 后缀） |
| 应用私有目录落盘 | `libgstore_mod_<name>_<major.minor.patch>.so`（**不带** ABI 后缀） |

资产名中的版本与模块 `Cargo.toml` 的原始版本可能不同（原始版本保留 `+build`），
但**资产名恒为三段纯数字**，宿主才能解析。`asset` 字段是 Release 资产名，
**绝不复用**本地落盘文件名。

### 2.2 清单 v2（`modules.json`）

Flat 清单结构（Dart `ModuleManifestV2.fromJson` 消费）：

```json
{
  "version": 2,
  "modules": {
    "qr": {
      "version": "1.2.3",
      "min_host_abi": "2",
      "abi": {
        "arm64-v8a": {
          "asset": "libgstore_mod_qr_1.2.3-arm64-v8a.so",
          "sha256": "<hex>",
          "size": 123456
        }
      }
    }
  }
}
```

约束：

- `version` 必须是 `2`。旧 schema（含 `file_name`）会被**显式拒绝**并安全降级，不崩溃。
- 单个 ABI 条目缺 `asset` / `sha256` / `size` 时跳过该 ABI，不影响其他 ABI。
- 零字节 `.so` 不进入清单；GPU 变体（`_opencl` / `_vulkan` / `_cpu`）不进入 Flat 清单。
- 清单**不含** `variants` 字段。

### 2.3 内置清单（`modules_builtin.json`）

随 APK 打包，声明内置模块版本，用于「远端 vs 内置」比较与 `probe` 展示：

```json
{
  "qr": { "version": "1.2.3", "abi": { "arm64-v8a": "1.2.3" } }
}
```

写入路径：`assets/app/modules_builtin.json`。

### 2.4 IT-Tools 清单（`it_tools.json`）

```json
{ "contentHash": "<zip 字节的 sha256>", "asset": "it-tools.zip", "size": 123456 }
```

`contentHash` 是 zip 字节的 SHA-256，`asset` 固定为 `it-tools.zip`。
内容变更自然由内容哈希区分，**不再依赖应用版本号**做标记。

## 3. 发布流程与上传顺序

发布由 `.github/workflows/build.yml` 在同一 Release 上完成。上传顺序**固定不可交换**：

1. **本次各 ABI 新 `.so`**：按 `modules.json` 逐项上传，资产名用版本化名，
   允许 `--clobber`（tag 复用时同名资产会重复上传）。上传前校验文件非零字节，
   且 sha256/size 与清单一致，不符即中止发布。
2. **`modules.json`**：最后上传，作为**提交标记**（commit marker），允许 `--clobber`。
3. **APK / AAB** 与 **it-tools 资产**（`it-tools.zip` + `it_tools.json`）。
4. **清理旧模块资产**：见下方留存策略。

约定：任何模块内容变更**必须提升模块 `version`**。`--clobber` 仅是「同版本重建」的兜底；
客户端按「同版本但 sha256 变化」规则仍能取到修正版本。

删除旧资产前必须保证不删掉本次清单引用的文件，因此顺序是「先传新 `.so`，再传清单，最后清理」。

### 3.1 留存策略

CI 变量 `MODULE_MANIFEST_TTL_DAYS` 默认 `30`。清理步骤在清单上传**之后**执行，规则：

- 只考虑 `libgstore_mod_*.so` 形式的模块资产。
- 已被本次 `modules.json` 引用的资产**永不删除**。
- 创建时间**早于 TTL（默认 30 天）**的未引用模块资产才删除（`gh release delete-asset`）。
- `it-tools.zip` 与 `it_tools.json` **豁免**，绝不在清理范围内。

> 注意区分两个 TTL：CI 侧的资产留存 TTL 是 **30 天**；客户端清单缓存 TTL 是 **24 小时**（见 §4.3）。

## 4. 客户端的信任与获取链路

### 4.1 信任锚（`ModuleManifestClient`）

清单是哈希的来源，因此清单本身必须经独立、可信的通道获取：

- 只用 `dart:io HttpClient`，保持 **默认证书校验**。
- **不设置** `badCertificateCallback`（不关闭证书校验）。
- **不施加** `getProxy()`，也不经任何代理前缀。
- **不使用**项目内基于 Dio/rhttp 且 `allowBadCertificate: true` 的 GitHub 客户端
  （`GithubRestClient` / `DioClient`）。它们允许自签名证书并带代理逻辑，会污染信任锚。

请求入口：`https://api.github.com/repos/sunO2/GStore/releases/latest`。

- 仅取**稳定版**：`releases/latest` 返回 `prerelease == true` 时视为无可用 Release。
- `modules.json` 与 `it_tools.json` 均从**同一 Release**、经**同一未代理、校验证书**的客户端获取。
- 模块 / IT-Tools 资产 URL 取自 Release 的 `assets[].browser_download_url`
  （按清单资产名精确匹配），**不假设** `$base/<abi>/<file>`。
- 若某资产名在 Release 元数据里未命中，失效 Release 缓存并**恰好重解析一次**。
- 任何网络 / 解析失败一律返回 `null` 或已校验缓存，**绝不抛异常**。

### 4.2 代理信任规则（`ModuleDownloader`）

资产字节可以经 GitHub 代理加速，但代理绝不被信任：

- **先校验代理前的原始 URL host**，必须命中资产域白名单（裸 host，点边界匹配：
  `host == w || host.endsWith('.$w')`）：

  ```
  github.com
  api.github.com
  objects.githubusercontent.com
  release-assets.githubusercontent.com
  githubusercontent.com
  ```

- 只有原始 URL 通过校验后，才把 `getProxy()` 作为**固定前缀**拼到该已校验 URL 前面。
- **代理 host 不参与白名单判定，也不得被视为可信来源**。代理 host（如 `gh-proxy.org`）
  绝不加入白名单。
- `getProxy()` 为空串时直连已校验的原始 URL。
- `followRedirects = false`，手工逐跳跟随重定向；**每一跳的目标 host 都必须重新通过白名单校验**，
  跳数有界。
- 代理返回的字节一律以**清单记录的 sha256** 为准，下载器本身不做完整性判定。
- 有限重试 + 退避（仅 403/408/429/5xx 与超时/连接错误）；整体大小有上限；写 `.tmp`。
- 同一 URL 的并发下载共享同一个 `Future`，只发一次网络请求。

一句话：**代理只能给「原始 host 已通过校验的资产下载」做前缀加速；代理本身永远不是信任来源。清单（`modules.json` / `it_tools.json`）绝不经过代理。**

### 4.3 缓存 TTL 与 ETag / 304

清单磁盘缓存位于应用支持目录：

```
<support>/gstore_modules/_cache/modules.json
<support>/gstore_modules/_cache/.etag
<support>/gstore_modules/_cache/.fetchedAt
<support>/gstore_modules/_cache/it_tools.json
<support>/gstore_modules/_cache/it_tools.etag
<support>/gstore_modules/_cache/it_tools.fetchedAt
```

- TTL 默认 **24 小时**。缓存新鲜且未强制刷新时**零网络**。
- 过期时带 `If-None-Match`（上次 ETag）请求；返回 **304** 则复用缓存正文，
  只刷新 `fetchedAt`，不重新下载 body。
- **403 / 离线 / 超时**等情况回退到此前已校验的缓存清单；无缓存则回退 `null`。
- 下载资产返回 404 时，失效清单并**恰好重解析一次**。

### 4.4 完整性：下载、安装与挂载复核

原子安装顺序不可交换（`ModuleLoader._downloadAndInstall`）：

1. 下载到 `<support>/gstore_modules/<name>/<finalSo>.tmp`。
2. 校验清单 SHA-256：不符则删 `.tmp`，**不产生**最终 `.so` / `.meta`。
3. **先** rename `.tmp` 为 `libgstore_mod_<name>_<major.minor.patch>.so`（三段纯数字）。
4. **后**写 `.meta`（`{name, version, abi, sha256, source:'remote'}`）作为提交标记。
5. 仅在 `requireSignature = true` 时写非空 `.sig`；`false` 时删除同名遗留 `.sig`。

安装目录与缓存统一位于 `getApplicationSupportDirectory()/gstore_modules/**`。

**挂载期 fail-closed**：已下载文件在 `dlopen` 前由 Dart 复核 `.meta`：

- `.meta` 存在、`name` 匹配、且 `.meta.sha256` 与 `.so` 字节的 SHA-256 一致，才挂载。
- 缺 `.meta` / `.meta` 非法 / sha256 不匹配 → **不挂载**，写 `<moduleDir>/quarantine.json`，
  解析期跳过该版本并回退内置或重新下载。
- 启动清理下载目录中上次中断遗留的 `.tmp`。

同步路径（`ensureModule`）在存在已挂载、有效已下载产物或内置产物时**零网络**；
远程刷新与更新放在后台 `downloadAndInstall()`，**只下载安装、不挂载**，下次启动生效。
`rollbackToBuiltin(name)` / `clearDownloadedModule(name)` 提供回退与清除。
`isAvailable` / `probe`：内置恒为可用；已下载要求 `.meta` 有效、sha256 复核通过且未被隔离。
`download` 内核模块**禁止**经同步路径自举下载。

## 5. requireSignature 状态与 Phase 2 步骤

### 5.1 Phase 1（当前）

- `requireSignature` 默认 **`false`**。
- **尚未实现 Ed25519**：`rust/gstore_host/src/trust.rs` 的钉死公钥
  `MODULE_SIGNING_PUBKEY_HEX` 仍为**空字符串**，即任何携带 `.sig` 的模块都会被宿主拒绝。
- 因此 Phase 1 下载安装：
  - **绝不写空 `.sig`**；
  - `requireSignature = false` 时，任何本地 `.so` 挂载前都会删除同名遗留 `.sig`
    （否则宿主会走签名分支并用空公钥拒绝加载）。
- 本阶段的完整性保证是 **SHA-256 同源校验**（清单与载荷同源，见 §7 已知风险）。

### 5.2 Phase 2 步骤

1. 发布端离线生成 Ed25519 密钥对，公钥填入 `MODULE_SIGNING_PUBKEY_HEX` 并随版本固化
   （签名脚本：`rust/sign_module.py`）。
2. 发布流程对每个模块资产生成非空签名，写入清单条目（`abi.<abi>.signature`）。
3. 宿主把 `requireSignature` 置为 `true`。
4. 启动时执行 `migrateUnsignedDownloadedModules()` 清理 Phase 1 的无签名下载产物
   （见 §5.3）。
5. 此后 `requireSignature = true`：清单缺非空 `signature` 即拒绝安装（fail-closed）；
   安装成功时写入非空 `.sig`。

### 5.3 无签名产物迁移（`migrateUnsignedDownloadedModules()`）

背景：宿主信任门把「无 `.sig`」的模块视为随包内置、直接放行。因此启用签名前，
必须把 Phase 1 遗留的无签名**下载**产物隔离，否则它们会被当作内置模块挂载。

规则：

- 仅 `requireSignature == true` 时执行；`false` 时立即返回，**零副作用**（不扫描、不写、不删）。
- 扫描 `<support>/gstore_modules/<name>/` 下**带 `.meta`** 的 `.so`，即 downloaded-module set
  （`.meta` 是远程安装的提交标记；内置解压产物无 `.meta`，不在扫描集合，绝不触碰）。
- `.sig` 缺失 / 空白 / 非 128 位十六进制，即视为无效签名，写 `quarantine.json` 标记隔离，
  下次解析跳过并回退内置或重新下载。
- **不删除**任何产物；方法幂等，重复调用不会重复写入或损坏 `quarantine.json`。
- `download` 模块遵循同一规则（其远程更新在存在本地/内置产物后允许）。
- 由 `ensureModule` 启动时经 `_migrateSignaturesOnce()` 恰好执行一次，且**先于**本地产物解析。

## 6. IT-Tools 远程更新

远端 `it_tools.json`（同 Release，经 §4.1 未代理校验证书通道）驱动更新：

1. 解析本地标记 `{contentHash, source}`（`source` = `remote` / `asset`）。
2. 用 `ModuleDownloader` 下载 zip，先校 `size` 再校 `contentHash`，任一不符都不触碰当前目录/标记。
3. 解压到 `it_tools.new`，入口 `index.html` 缺失即失败。
4. 原子换名：旧当前目录改名为 `it_tools.prev`，`.new` 提升为当前，随后写标记。
5. 失败/离线回退链：当前目录 → `it_tools.prev`（上次可用远端）→ 随包资产（`source=asset`）。
6. 清理/统计覆盖当前目录 + `.prev` + `.new`；**WebView 存活期间不删除当前目录**
   （`beginUse`/`endUse` 存活保护，清理延迟到最后一个使用者释放后执行）。

详见 `document/development/12-开发者工具箱-IT-Tools离线内嵌.md` §8。

## 7. 已知风险（务必阅读）

本阶段的完整性保证有明确边界，以下风险**未被消除**：

1. **同源 SHA-256 只保证完整性，不保证真实性。**
   哈希来自清单，载荷也来自同一渠道。若攻击者同时攻破清单与载荷（把哈希与文件一起改掉），
   SHA-256 校验会被绕过。这正是 Phase 2 签名要解决的问题。
2. **本阶段无法阻止本地沙箱同时改写 `.so` 与 `.meta`。**
   挂载复核的是「`.meta.sha256` 与 `.so` 字节一致」，两者都在同一应用私有目录内。
   能同时改写两者的本地攻击者（等于已取得应用沙箱写权限）可以伪造这对文件。
   挂载复核防的是「只改 `.so`」或「只改 `.meta`」的半写/篡改，不是防一个完整的本地攻击者。
3. **缓存清单 `<support>/gstore_modules/_cache/modules.json` 未做静态认证。**
   它明文存在沙箱内，可被本地改写。但**单独篡改缓存清单不构成 RCE**：
   挂载仍以**安装时写入的 `.meta.sha256`** 对 `.so` 字节复核为准，
   清单只影响「下载什么 / 期望什么哈希」，改清单不会让一个未通过 `.meta` 复核的文件被挂载。
4. **`dlopen` 可致 RCE。**
   加载的原生 `.so` 在应用进程内拥有与宿主相同的权限；一旦恶意模块被执行，
   等同于任意代码执行。上述所有校验都是这条防线之前的门禁，漏洞会让门禁失效。
