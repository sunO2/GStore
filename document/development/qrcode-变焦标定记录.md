# 扫码变焦（焦距调节）标定记录

**日期**：2026-09-12
**范围**：`lib/page/qr_tool/`（`view.dart` + `zoom_controller.dart`）+ `rust/gstore_mod_qr`
**结论**：变焦决策已从「单帧几何 + 固定阈值」改为「实测数据驱动」，真机 decodeRate 从 ~3.7% 提升到 ~19~23%，且不再跑飞。

> 设计与目标能力见 [qrcode.md](./qrcode.md)；本文只记录**实际实现的调参与标定依据**。

---

## 1. 问题

- 二维码识别失败率高
- 长焦/近焦（变焦）调节算法不稳定

变焦这块历史上被反复打补丁但**零自动化测试**：

```
1eca289 feat: 码眼自动变焦/绘制
b8cba9a feat: 自动变焦升级为闭环状态机 + 边界距离引导
7a2d6cc fix: 单码眼变焦死循环放大 — 增加码眼位置判据分远近
8086355 fix: 扫码对焦不准确 — 对焦跟随码眼中心 + 变焦后重新对焦
8967854 fix: 变焦跳变修复 — 比例目标控制一步收敛 + 对焦/变焦解耦
f5860cc feat: 解码引擎替换为 zxing-cpp + 焦段/对焦优化
```

## 2. 根因（逐条都有真机数据佐证）

1. **单帧判据 + 只 2 帧去抖**：手机倾斜时四角包围盒面积骤变，噪声直接进决策。
2. **动作后只用 200ms 限频**，并用未稳定的帧再评估；`_currentZoom` 还是乐观赋值 → A→B 后立刻判 B→A，形成极限环。
3. **单步上限 2.0×**：面积 ∝ 倍率²，一步可过冲 4 倍，必被反向拉回。
4. **不可读候选的角点也拿去算占比**，置信度低却是决策输入。
5. **阈值是常数**（0.35/0.80/0.55），注释里自己都写了换 zxing-cpp 后重新校准过、旧值不可沿用。
6. **从未记录「上一档焦距的解码成功率」** → 不知道往哪走、走到哪停。
7. **学习成果会丢**：`_initCamera` 每次都新建控制器，切「生成/识别」或重进页面就把学到的焦段清空。
8. **占比信号在远距离小码时不可靠**：真机出现 `meanRatio` 相对倍率**非单调**
   （1.75 档 0.016 → 2.2 档 **0.002** → 2.86 档 **0.023**）。符号只有十几像素时，
   四角定位差几个像素就能让包围盒面积翻几倍。

## 3. 数据管线

### 3.1 Rust 侧新增解码证据（`gstore_mod_qr`）

`barcode_json` 增加三个字段，让宿主能区分「完全可读 / 定位到但取样失败 / 码制问题」：

| 字段 | 取值 | 意义 |
|---|---|---|
| `is_valid` | bool | 是否真的解出 |
| `error` | `none`/`checksum`/`format`/`unsupported` | **`checksum` = 定位/取样成功但校验失败**：几何可信、像素质量不足 → 是「该调焦段/该提对比度」的强信号，与「完全没检测到」完全不同 |
| `orientation` | 度 | 符号朝向 |

### 3.2 逐帧遥测（可导出调参）

| 日志 | 内容 |
|---|---|
| `QR_ZOOM` | 每次变焦动作/边界：zoom、ratio、emaRatio、detected、checksumError、sharpness、action、target、applied、zoomIneffective、levelGood |
| `QR_ZOOM_STATS` | 每次识别成功的**分档实测统计**：每档 frames / detected / decoded / checksumErrors / degenerate / decodeRate / meanRatio / meanSharpness |

> `QR_ZOOM` 对同一动作做 1s 限频——`tooFar` 是**持续状态**，曾逐帧记录把日志环（2000 条）刷爆。

## 4. 最终控制律（`QrZoomController`）

决策输入只有一份「观测」：占比 + 当前倍率 + 是否检测到 + 是否 checksum 失败 + 清晰度。

| 机制 | 参数 | 作用 |
|---|---|---|
| 时序平滑 | `emaAlpha=0.35` | 占比用 EMA，单帧噪声不触发动作 |
| 共识门控 | `consensusFrames=3` | 连续 3 帧同向才动作；无检测/几何退化帧会重置共识 |
| 动作后静默期 | `settleFrames=3` | 变焦后丢弃 3 帧，等镜头/数字变焦真正反映到图像 |
| 步长阻尼 | `0.8 ~ 1.3` | 单步不超 1.3×，防过冲回拉 |
| 反冲验证 | 连续 2 次不符 | 动作后占比没按预期变化 → 判定「变焦无效」停止放大 |
| 分档统计 | 0.25 档粒度 | 每个焦段的实测解码率/清晰度，导出后离线调参 |
| **实测标定停手线** | `successMargin=0.8` | 停手线 = 实测可解占比 × margin。**margin 必须 < 1** |
| **档位够用把关** | ≥5 帧且成功率 ≥0.15 | 已实测证明能解的档位**不再动** |
| 起始倍率 | `preferredStartZoom` | 有成功记录用该倍率，否则 1.0 |
| 学习结果共享 | `QrZoomLearning`（按相机） | 切模式/重进页面不丢 |

### 关键：为什么 `successMargin` 必须 < 1

停手线的语义是「**已经知道这个尺寸能解出码，就不该再要求更大**」。
早期取 3.0（要求达到已验证尺寸的 3 倍才停手），结果是**逼着算法爬过已经证明能用的档位**：

> 真机：1.69 档成功两次（占比 0.012）→ 停手线被算成 `0.012×3=0.039` → 算法认为 0.012「还太小」
> → 继续放大 → 一路到数字变焦上限 4.0（那里占比也只有 0.02，永远够不到 0.039）→ 无限 `tooFar`。
> 该档位刷了 283 帧、decodeRate 仅 **2.1%**，而最好的档位（1.69，**33%**）被它径直越过。

### 关键：把关按「档位」作用域，不按「会话」

一次成功就会停止扫描，用户点「重新扫描」会**回到同一档位**。
若按会话清零，就永远攒不够 5 个样本、也就永远无法判定「这一档其实够用」——这正是早期「证据用不上」的原因。

变差时无需额外复位：失败帧持续累积会把成功率拖到 0.15 以下，把关自动放开（实测约 1~2 秒）。

## 5. 真机实测数据

### 5.1 修复前后（同一台设备）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 起始倍率 | 0.67（超广角，最小倍率） | **1.0**（或上次成功倍率） |
| 首次成功 | 从 0.67 爬 ~5 步 | **1 帧** |
| 最佳档 decodeRate | 0.037 | **0.19 ~ 0.33** |
| 每次重扫 | 打回 0.67 重爬 | 沿用学到的档位 |

### 5.2 阈值标定依据

| zoom 档 | frames | decoded | decodeRate | degenerate | 判定 |
|---|---|---|---|---|---|
| 1.00 | 3 | 0 | 0.0 | 0 | 放大 |
| 1.25 | 6 | 0 | 0.0 | 0 | 放大 |
| **1.75** | 4~20 | 2~5 | **0.21~0.33** | 0~26% | **可用** |
| 2.25 | 86 | 3 | 0.034 | **80（93%）** | 不可用 |
| 3.75 | 6 | 0 | 0.0 | 0 | 不可用 |
| 4.00 | 283 | 6 | 0.021 | 104（37%） | 不可用（已到上限） |

→ **可用档位 0.21~0.33，不可用 0.0~0.034**，`zoomGoodRate=0.15` 能干净分开。
→ 成功解码的占比集中在 **0.013~0.069**，原阈值 0.35 是它的 5~25 倍（过高）。

## 6. 踩过的坑（勿重犯）

| 坑 | 表现 | 修正 |
|---|---|---|
| `successMargin` 取 > 1 | 已成功的档位仍被判「太小」，爬到变焦上限卡死 | 改为 0.8 |
| 给停手线加「绝对下限」 | 该下限是个**逼着继续爬**的量，把问题放大 | 已删除 |
| 变焦评估放在解码**之前** | 读的是上一帧证据，`checksumErrors == frames` 恒等（成功那帧被记成校验失败） | 挪到解码之后，用同帧证据 |
| `decodeRate` 分母不含成功帧 | 成功即 break、不走逐帧观测，比值偏高、语义混乱 | 分母补上成功帧 |
| 用「最小成功占比」标定 | 一次极小尺寸侥幸成功就把停手线压到底 | 改中位数 + margin<1 |
| `_initCamera` 重建控制器 | 切模式/重进页面后 zoom 从 2.86 掉回 1.0 | `QrZoomLearning` 按相机共享 |
| 持续状态逐帧记日志 | `tooFar` 刷爆日志环，挤掉有用记录 | 同一动作 1s 限频 |
| 多 ROI 提前 return | 主 ROI 检测到候选就 `return null`，放弃另两个 ROI，白丢识别率 | 改为继续尝试其余 ROI |
| 成功判定只看 `text` 非空 | 可能把「带部分文本但校验失败」的码当结果返回 | 优先 `is_valid`，旧模块回退 |

## 7. 遗留待查

- **`degenerate`（检测到符号但四角退化、占比不可用）**：1.75 档 26%、2.25 档 93%、4.00 档 37%，
  看起来随倍率上升。需确认是四角定位在高倍率下真的退化，还是 `_eyePoints` 在某条早退路径上留了脏数据。
  目前这类帧无法驱动决策（会重置 EMA 与共识），所以只影响观测量，不影响稳定性。
- 若后续想进一步压低解码耗时，可考虑把「多 ROI + 多二值化」的尝试顺序也纳入统计驱动。
