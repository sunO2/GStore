# 14 · 渠道详情页「历史构建」：确认后只切数据、不触发下载

> 适用范围：Hybrid 详情页的「更多 → 历史构建」入口（`ChannelBuildHistorySheet`）。
> 相关脚本：`scripts/channels/src/pingan/detail.js`（`jsBuildHistory`）。

## 1. 现象

在详情页「更多 → 历史构建」里选中某条构建、点确认后，**同时发生两件事**：

1. 详情页数据被全量刷新为该构建（预期内）
2. **直接开始下载该构建**（非预期）

期望：确认后**只切换数据**（下载区显示为该构建），下载由用户在下载区自行触发。

## 2. 根因

调用链（确认按钮 → Flutter 回调）：

| # | 位置 | 行为 |
|---|---|---|
| 1 | `lib/core/design/channel_build_history_sheet.dart` | 底部按钮「确认下载」→ `pop(选中构建)` |
| 2 | `lib/page/detail/detail_ui_mixins.dart` `showBuildHistory()` | 收到选中构建 |
| 3 | 同上 · `dc.switchVersion(..., build: {num, ipaName})` | 拉该构建的详情数据 |
| 4 | 同上 · `await refreshDetail(detailData: detail)` | **数据切换**（`DetailLogic.refreshDetail` 仅替换 `state.detailInfo`，无副作用）|
| 5 | 同上 · 匹配下载项 → `await startDownload(match)` | **触发下载 ← 根因** |

第 4、5 步连在一起执行，所以确认一次 = 刷新 + 下载。

补充：脚本侧 `jsBuildHistory` 的注释写明设计意图是「不再 refreshDetail 全量重拉，
只走 `updateDownloadList` 局部更新」——但 Flutter 侧 `showBuildHistory` 固定
`return null`，脚本拿不到选择结果，那段逻辑实际不会执行。**当前行为完全由 Flutter 侧驱动**，
这一点决定了修复必须落在 Flutter 侧。

## 3. 改动

1. `lib/page/detail/detail_ui_mixins.dart` `showBuildHistory()`
   - 删除第 5 步（下载项匹配 + `startDownload`）
   - 错误文案 `该构建暂不可下载` → `该构建暂不可切换`
   - 保留第 3、4 步 → 语义变为「只把详情数据换成所选构建」
2. `lib/core/design/channel_build_history_sheet.dart`（文案与行为对齐，否则 UI 在骗人）
   - 副标题：`选择历史构建，确认后详情下载区切换为该构建（不会自动下载）`
   - 确认按钮：`确认下载` → `确认切换`
3. `test/channel_build_history_sheet_test.dart` 同步 6 处 `确认下载` 断言

## 4. 明确不动的部分（避免改坏）

- **脚本侧 `jsBuildHistory` 未改**：它 `host.ui.call('showBuildHistory')` 拿到的是 `null`
  （Flutter handler 固定返回 null），后续 `updateDownloadList` 分支是既有死代码；
  行为不经由它，改动它反而引入风险。若将来要让脚本真正接管局部更新，
  需要先把 handler 的返回值契约改成 `{ok:true, data:{num, ipaName}}`，属独立议题。
- **「切换版本」选择器里的历史构建行未改**：`showVersionPicker` 的
  `onBuildSelect → _downloadHistoricalBuild` 是另一个入口（版本选择器内展开的构建行，
  点击即下载、没有确认步骤），与本次现象不对应。**如需一并调整，属新增需求。**

## 6. 遗留

- 脚本侧 `jsBuildHistory` 的选择结果回传契约与局部更新分支仍是死代码（见 §4），
  当前无害；若后续要降低刷新开销，应作为独立改造处理。
